# Analysis — the ablation ladder is the paper

Everything in this folder is generated by a script and then annotated by hand.
The annotation is the work; the scripts only remove the excuse not to do it.

## The ladder

BTC's published research question, roughly: *under a 4B parameter ceiling and ~10k
examples, where does pure deep learning stop paying off, and where does an LLM-based
approach start to?*

Measured on **one fixed dev split**, this ladder answers it directly:

| # | System | Script | Expected role in the story |
|---|---|---|---|
| 1 | BM25 | `phases/1_bm25/bm25_baseline.py` | lexical floor; strong on statute numbers |
| 2 | + tuned k1/b, chunking | `phases/1_bm25/grid_search.py` | how much is free from preprocessing |
| 3 | Dense, zero-shot | `phases/2_dense/zero_shot_eval.py` | does off-the-shelf semantics beat lexical? |
| 4 | Dense, fine-tuned | `phases/2_dense/train_biencoder.py --round 1` | value of in-domain supervision |
| 5 | + hard negatives | `--round 2`, `--round 3` | value of negative quality |
| 6 | + hybrid fusion | `phases/2_dense/hybrid.py` | are the failure modes complementary? |
| 7 | + cross-encoder rerank | `phases/3_rerank/rerank.py` | value of joint query-document attention |
| 8 | LLM-based reader | `phases/4_task2_qa/baseline_generative.py` | where generation starts to pay |

**Every rung must be measured on the same dev split with the same cutoff procedure.**
A ladder where rung 3 used a different split is not an ablation, it is a collection of
anecdotes.

## Error analysis discipline

At the end of **every** phase:

```bash
python tools/error_analysis.py --run work/experiments/runs/<best>.jsonl --phase 2 -n 20
```

This produces three things. The middle one decides what you work on next.

### The loss decomposition — read this before choosing your next task

Every point of missing Recall is attributed to exactly one cause, and the
components provably sum to the gap:

```
recall + loss_cap + loss_retrieval + loss_ranking + loss_cutoff + loss_zeroed = 1
```

| component | meaning | what fixes it |
|---|---|---|
| `cap` | more than 5 gold documents for that question | **nothing** — impossible by rule |
| `retrieval` | gold never returned by the retriever | the **retriever**; a reranker cannot reach it |
| `ranking` | retrieved, but ranked below position 5 | the **reranker** or fusion weights |
| `cutoff` | sitting in the top-5 and not returned | the **cutoff rule** — free, one sweep |
| `zeroed` | empty or >5 ids, so BTC scored it 0 | **self-inflicted**; clamp the cutoff |

A report reading *"0.19 retrieval, 0.09 ranking, 0.04 cutoff"* tells you to spend
the week on the retriever — and that the reranker has at most 0.09 to give, no
matter how good it gets. The derivation is in [`src/analysis.py`](../../src/analysis.py);
the identity is asserted over 2000 randomised cases in
[`tests/test_cases.py`](../../tests/test_cases.py).

The report also contains: integrity alarms (which invalidate everything below
them), nested ceilings, a full cutoff what-if table, breakdowns by gold count /
gold rank / question length / answer-set size, an optional `--compare` against an
earlier run listing exactly which questions improved and which regressed, and a
worksheet of the worst N questions with the dominant loss pre-computed.

**The worksheet is still yours to fill in.** The script says which *kind* of fix
applies; only you can say *why* the model made that mistake, and that is the part
the paper needs.

BTC explicitly asked for analysis of *why* a method underperformed and what the next
method fixed. Twenty labelled failures per phase is enough to write that section — and
few enough that you will actually do it.

The categories that recur in Vietnamese legal IR:

| Category | What it looks like | Usually fixed by |
|---|---|---|
| `granularity` | right văn bản, wrong điều | chunking change |
| `lexical-mismatch` | "nghỉ phép năm" vs "nghỉ hằng năm" | dense retrieval |
| `multi-article` | answer spans several điều, we returned one | cutoff rule / min_k |
| `negation` | retrieved article states the opposite condition | cross-encoder |
| `numeric` | matched Điều 12 instead of Điều 112 | BM25 weight in fusion |
| `ambiguous-query` | question under-specified | nothing — report it |
| `label-noise` | our answer looks right, gold looks wrong | nothing — report it |
| `cutoff` | gold ranked 2nd but fell outside the set | re-sweep the cutoff |

The last three matter as much as the first five: a phase where 6 of 20 failures are
label noise tells you your remaining headroom is smaller than the score suggests, and
that is a finding worth stating.

## Building the ablation table for the paper

```bash
python -c "
import pandas as pd
d = pd.read_csv('work/experiments/runs.csv')
cols = ['run_id','chunking','retriever','negatives','reranker','cutoff_rule',
        'dev_R','dev_P','leaderboard']
print(d[cols].to_markdown(index=False))" > analysis/ablation_ladder.md
```

If a row you need is not in `runs.csv`, that experiment did not happen. Re-run it.
